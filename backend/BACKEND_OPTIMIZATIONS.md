# 历史读取、诊断与旧流程整理

数据库已应用 001～005 的项目，需要按序执行新增的 `006_history_reads.sql`、`007_history_pagination.sql`。迁移只新增读取函数，不删除或重写旧消息、额度与订阅数据。首次安装仍按顺序执行全部迁移。

## 结果

- 006 把历史读取接口原有的两次会话限流与所属数据读取合并为一个数据库往返。Google 验证、全局限流和测试账号绑定保持原有流程；缺失新 RPC 时仍走原有限流路径。
- 取消轮询间隔依次为 0.5、1、2 秒，之后保持 2 秒；提交回复仍由数据库检查请求是否有效。实际停止延迟还取决于数据库响应。
- 异常日志记录操作、异常类型、安全错误码与服务端请求编号。响应的 `X-Request-ID` 可用于查日志；不记录异常原文、密钥、SQL 参数或聊天内容。
- 新前端每页加载 50 条消息，通过“加载更早消息”读取前页并保持阅读位置。失败保留已显示的消息和游标，可以重试。
- API `GET /conversations/{id}?limit=50&before=70` 返回 `messages`、`has_more`、`next_before`、`total`。游标是前页结束位置，追加新消息不会改变既有游标。`limit` 范围 1～100，`before` 必须非负。
- 为兼容旧客户端，不带 `limit` 的历史接口仍返回全部消息。模型上下文使用独立的所属数据查询，最多传输最近 40 条；旧数据库暂时回退到原读取方式。

## 数据结构与兼容

消息继续存放于现有 JSONB 数组，避免这次整理引入全量数据搬迁。分页减少传输和前端渲染；数组追加的数据库更新成本仍存在。若长对话规模继续增加，再以独立迁移引入消息表，不应直接改写已执行的旧迁移。

旧公开图片抓取器和未调用的单条消息写入/旧请求启动方法从应用代码清理。私有 `/assets/{uuid}` 的所属校验、格式校验和下载仍保留。历史 SQL 保留，以支持逐步迁移和旧版本兼容。

生产 SQL 无本地执行通道时，在 Supabase SQL Editor 执行迁移。合并副本保存在忽略目录 `.local/apply-backend-optimizations.sql`；只执行一次，若已执行 006，则仅执行 007。
