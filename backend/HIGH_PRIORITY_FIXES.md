# 高优先级修复交付（2026-10-17）

本次仅处理生成失败恢复、预算与用量、图片归属和清理。中低优先级功能未扩展。以下是本地代码与验证结果，不表示已部署或完成真实服务联调。

## 生成可靠性

- `request_id` 与请求内容摘要存入数据库。重复成功请求返回原结果；执行中返回状态；修改内容或复用失败编号拒绝执行，避免隐式二次付费。
- 新会话创建和请求登记在同一事务中。同一会话仍只允许一个有效生成任务。
- 用户消息、AI 消息、图片绑定、成功结果在一个数据库事务中提交。失败、取消或超时不会只保存半轮对话。
- `GET /generations/{request_id}` 只允许所属用户查询。取消和删除会话后，迟到回复不能写入。
- 浏览器短暂断线不直接取消服务器生成。前端查询原编号恢复结果，刷新页面后也可点击 Recover reply。结果不明时阻止再次发送；确认失败后恢复草稿。前端切换会话或账户仍会主动停止旧任务。
- 进程崩溃后的任务在 150 秒租约到期后视为失败。没有外部持久任务队列，不能在进程崩溃后继续推理；用户需明确重新发送。上游已发生的计算可能仍收费。
- 最终清理失败不会覆盖已提交的成功结果；未知提交状态可从状态接口确认。成功记录不要按旧的“一天后删除请求记录”示例直接清除，否则会丢失幂等边界。

## 用量与预算

- 输入先计数，包含系统提示词和 128 token 的结构余量；超过输入上限拒绝调用生成。输出设置 `max_output_tokens`，候选数固定 1。
- 每个模型必须配置 `MODEL_BUDGETS_JSON`，缺失或非法时返回 503，默认 `{}` 不调用生成接口。代码不猜测模型价格。
- `input`、`output` 单位为 USD / 百万 token，必须填该模型可能采用的最高费率，包括多模态、思考、长上下文等适用计价。图片模型还必须填写 `image_micro_usd`，作为每次请求的额外图片收费上界；这不是单张图片价格。只开放已确认计数、输出限制和计价规则的模型。
- 每次调用按“计数输入 × 输入费率 + 最大输出 × 输出费率 + 图片额外上界”向上取整预留微美元。同一事务检查用户每日预算、全站每月预算、用户每日请求数。
- 预留成功后，即使超时、取消、上游报错或实际回复很短，也保留全部预留额，不自动返还。这是保守准入额度，不是实际账单；实际 `usage_metadata` 另行保存。
- 默认：用户每日 1 USD、全站每月 10 USD、用户每日 50 次；每日/月度按 UTC 划分。旧游客 8 次尝试及网络限制继续生效。请求次数预算统计到达付费准入的请求。
- 图片上传和生成图片共同受每日用户 20 MiB、全站每日 200 MiB、受管对象合计 1 GiB 限制；数据库先原子预留字节并登记对象，再写 R2。失败上传也保留当天额度，总存储额度在清理成功后释放。
- 以上是按管理员配置费率建立的应用准入预算。价格配置不正确、提供商计价变化及其他应用共用 API key 的消耗不受本应用约束，不能将它等同于提供商账单硬限额。

## 图片访问与删除

- 新图片返回 `/assets/{uuid}`，数据库保存 owner 和 R2 私有对象键。前端携带身份获取图片字节，再用可撤销 blob 显示；下载、模型读取均先验证归属。
- R2 新对象按用户分目录：登录用户 `private/users/{完整身份的SHA256}/{图片UUID}`，游客 `private/guests/{完整身份的SHA256}/{图片UUID}`。标识由后端已验证身份派生，同一身份稳定一致；目录不包含邮箱。数据库 assets.user_id 与 object_key 可查对应关系。上传与 AI 生成图片共用此规则；旧对象继续通过已保存的 object_key 读取和清理，不自动搬迁。
- 图片只可绑定到所属用户的一个会话，提交时数据库再次校验，防止并发复用或跨用户绑定。
- 必须先在 Cloudflare 关闭该 bucket 的 r2.dev 和公共自定义域名访问，再设置 `R2_PRIVATE_BUCKET_CONFIRMED=true`。该变量是部署者的确认，应用无法代替 Cloudflare 平台设置。
- 旧公共 URL 不自动取得可信所有权，新接口拒绝直接读取；界面显示重新上传提示。旧历史文字保留。若需迁移旧图，应审核对象实际归属后复制并改写引用，不能根据客户端 URL 自动认领。关闭公共访问前，已泄露的旧公共地址仍可能被访问；本地代码不能撤销它们。
- 删除会话在同一事务中清除缓存结果、停止任务并把关联对象放入持久删除队列。R2 故障时队列保留，后续重试。
- 启用每小时任务：在 backend 目录加载生产环境后执行 `python cleanup_assets.py`。每次最多删除 100 个排队对象；未绑定会话的对象保留 24 小时后回收。对象清理是异步的，应用内删除不代表 R2 已立即抹除。
- 清理失败会记录警告，不吞掉队列。部署后应监测任务失败和积压；任务未启用时对象不会自行清除。

## 部署顺序

1. 更换此前进入 Git 的真实凭据，配置到部署环境或密钥管理服务。不要再把真实值提交到 Git；本地 `.env` 可以继续忽略保存。
2. 备份数据库，先在测试库依序执行 `migrations/001_maintenance.sql` 和 `002_reliability.sql`。新后端依赖 002，不能只发布代码。
3. 根据目标账户的计价规则配置模型预算，缩小 `ALLOWED_MODELS` 到已确认可用的模型；`.env.example` 提供所有新增变量和单位。
4. 关闭 R2 公共访问，确认旧图片重新上传/迁移方案，设置私有桶确认变量，配置每小时清理任务。
5. 配套发布新后端与前端，验证 Google 登录、文本和图片问答、断线恢复、停止、预算拒绝、跨用户读取拒绝、删除与队列重试。
